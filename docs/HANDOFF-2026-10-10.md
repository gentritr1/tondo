## WORKSTREAM 1 — Retention: "Crew-lite" (do this first)

**You are mid-brainstorm on this.** Approach A was chosen. The next step per the
`superpowers:brainstorming` architectural path is: present the design sections →
owner approves → write the spec to `docs/superpowers/specs/YYYY-MM-DD-crew-retention-design.md`
→ owner reviews → invoke `superpowers:writing-plans`. **Do not write product code
until the spec is approved.**

### What a crew is
A durable group that outlives a room. A room code dies ~60s after the table empties
(see `public/js/share.js` top comment — it already reasons about this and links to a
*new* table because the old one is dead). A crew fixes exactly that gap.

A crew has:
- a **durable id / shareable link** (unlike a room code),
- **members** = `{ chosen name + a device token }` — **no accounts, no login, no
  email**. The device token lives in `localStorage` (the app already stores
  `tondo.name`, `tondo.lastTable`, etc. — add e.g. `tondo.crews`). Clearing storage =
  rejoin as new; acceptable for a casual game.
- a **persisted lifetime tally** across sessions (pies played, wins per member).

### The loop (what creates the habit)
play a pie → **"Save to crew"** (create new or pick existing) → the shared result text
links back to the **crew** (alive) instead of a **room** (dead) → a friend taps it days
later → crew page shows the standing tally + a **"Start a table"** button → they
reconvene → tally grows → repeat.

### Build it so B slots on later without rework
Approach B adds live "who's online in this crew now" + a one-tap in-app "come play"
summon. The WS server is already connection-oriented, so presence is feasible later.
Design the crew data model and endpoints so presence is additive.

### Persistence (couples to hosting)
A crew is tiny data (a handful of rows). Owner's stack notes point at **Neon Postgres**
— good fit, and there's a `neon-postgres` skill + `data-persistence` playbook. Confirm
in the spec. Whatever is chosen must be a *durable* store (survives restarts), unlike
the in-memory `server/rooms.js`.

### Open questions the spec must resolve (don't guess — decide explicitly or ask owner)
- Exact crew data model + migration (this is persisted schema → check wipe/migration
  risk FIRST per CLAUDE.md §3).
- How "Save to crew" maps a finished pie's players to crew members (names can collide;
  device tokens disambiguate).
- Crew link format and how it enters the share text (extend `pieResultText` in
  `public/js/share.js`).
- What the crew page shows and where it lives in the client (new screen vs. lobby
  section).
- Abuse: a crew endpoint is a new public surface — rate-limit it like the rest
  (`server/limits.js` is the model).

### Acceptance criteria direction (make them observable in the spec)
e.g. "a pie saved to a crew, server restarted, crew page reloaded → tally persists and
is correct"; "share text contains a crew link that resolves to the crew page after the
room is gone". Name the verification method (device/runtime, not config) per CLAUDE.md §1.

## WORKSTREAM 2 — Hosting move (unblocks "fully online")

**Why:** Tondo is a long-lived Node process holding rooms in memory, one 250ms tick,
players on persistent WebSockets. **Vercel's serverless model has nowhere for an
in-memory room or a standing socket to live.** Vercel Hobby is also non-commercial-only,
which a marketed launch likely crosses.

**Direction:** move the WS server to a WS-native long-lived host — **Fly.io**
(recommended), Railway, or Render. Server is already clean, so this is mostly config +
deploy. Static `public/` can stay on a CDN. Carry the abuse fix (below) in the same pass.
**Owner approves the actual deploy** (outward-facing).

### Abuse fix to fold in (the one real residual from the audit)
`server/limits.js` is well-reasoned, BUT the wrong-code join throttle lives on a
`SocketLimits` created **fresh per connection** (`server/index.js:202`). Its reassuring
"42,000 guesses/sec → 0.5" is **per socket**. Nothing rate-limits new *connections* per
IP (only a 32 *concurrent* socket cap), so an attacker gets **5 free wrong guesses per
reconnect**, and the code space is small (~370,000 codes → a live room hit in ~740
guesses on average; see `CODE_WORDS` = 37 words × 10000). This seats you at a stranger's
table, not just detects it.
- **Fix:** a per-IP connection-rate budget that outlives the socket (small LRU keyed by
  IP), and/or widen the code space.
- **Verify with an authorized load test** against a server you control — the 740 figure
  and reconnect-reset path are *inferred from reading*, NOT yet reproduced. (Note: an
  earlier attempt to write an enumeration probe in-session was correctly stopped by a
  safety classifier; keep any test strictly local, authorized, and framed as a defensive
  load check.)

### What is already safe (do NOT re-audit or "harden")
The game **engine is authoritative**: `assertTurn` + `canPlay` validate every move
server-side, and each snapshot ships only the recipient's own hand
(`server/game.js:566` — `hand: me ? me.hand… : []`). Clients cannot play out of turn,
play illegal cards, or see opponents' hands. This is correct; leave it.

## WORKSTREAM 3 — UX polish loop (narrow, not a redesign)

The visuals are **good** (fluid scaling 320px→desktop, motion tokens, a11y live
regions, contrast gate, a headless shoot gate). Do NOT do a ground-up redesign. The
three worth a focused pass with `emil-design-eng` + `ui-ux-pro-max`:
1. **First-run** — rules auto-open before the first quick pie, but a new player still
   lands in a dense table. Ease the first-time read.
2. **Empty & loading states** — highest-severity UX-playbook items; audit the
   lobby-waiting and reconnect moments specifically.
3. **Reconnect feel** — "away — reconnecting" is functional but a dropped friend is the
   most anxious moment in online play; give more reassurance.

Each is ~an afternoon. Require **before/after screenshots** via the existing shoot
harness (`scripts/shoot.js`, `npm run shoot`) — no "feels better" acceptance (CLAUDE.md §2).

### Carried gotcha (do NOT "fix" this)
Four flourishes were deliberately moved to **linear** easing this week. The UX database
says "never linear for UI transitions" — that rule governs enter/exit. A 360° direction
sweep is **constant motion**, which both Emil's framework and the database assign to
linear. The divergence is correct and intentional.
